PHASE 2 — CONTROLLED WINDOWS JOB OBJECT ACCEPTANCE

Implemented boundary (not enrolled in application tool dispatch)
native/phase2-containment/JobRunner.cs
server/src/domains/securitySupervisor/phase2JobBoundary.ts

Native launcher verifies executable SHA-256 while holding a read handle without
write/delete sharing. Creates the target suspended, assigns it to an unnamed job,
and resumes only after successful assignment. Failure terminates the suspended
target. The job handle is non-inheritable; the explicit inherited-handle list
contains only the target's NUL input and bounded output pipe.

Job limits: KILL_ON_JOB_CLOSE; active process count; per-process and aggregate job
memory; per-process and aggregate user CPU time; CPU rate hard cap; all eight basic
UI restriction flags. Neither breakaway nor silent breakaway is enabled. The helper
queries effective limits before launch and refuses mismatched readback. Normal root
exit, timeout, cancellation and output overflow terminate descendants. Successful
cleanup reporting requires the OS job active-process count to reach zero.

UI scope: job restrictions prohibit clipboard read/write, creating/switching
desktops, global atom access outside the job's atom table, changing system/display
parameters, exiting Windows and external USER handles. This is NOT a general claim
that every possible UI or desktop resource is isolated. The controlled fixture
attempted GetClipboardData and CreateDesktop; both returned access denied (5).
It never dereferenced clipboard data, switched desktops, injected input, displayed
UI, or exercised microphones/speakers. Other UI flags were queried, not physically
exercised. See Microsoft JOB_OBJECT_BASIC_UI_RESTRICTIONS documentation:
https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-jobobject_basic_ui_restrictions
CPU rate reference:
https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-jobobject_cpu_rate_control_information

Phase 1 binding
The supervisor registry binds the full canonical Phase 1 record digest and runtime
incarnation into every native request and response. An explicit invalidation writes
and fsyncs a tombstone, cancels active jobs and refuses registration/relaunch of that
incarnation, including after registry reconstruction. Tests use Phase 1 synthetic
records; no actual runtime measurement authority or protected identity service is
claimed. The validation callback and registry are supervisor-only facilities, not
worker/RPC APIs. Production integration and authenticated invalidation delivery are
not enrolled. Tombstones survive the tested registry reconstruction but their ACLs,
administrator resistance, whole-system crash durability and rollback protection
are not qualified by this phase. Restoring identity bytes cannot clear a tombstone.

Proof limits
Proves the exercised OS process lifetime/resource controls for these compiled,
reviewed fixtures and this Windows environment, plus synthetic Phase 1 binding and
tested incarnation invalidation. It is not a universal process-entrypoint closure.
Job Objects do not provide filesystem, network, credential or token isolation.
No untrusted third-party program, authenticated browser, installed runtime, vault,
credential access, deployment, physical UI/audio testing or Phase 3 work occurred.
The parent-kill test covers the running assigned tree, not every instruction-level
crash point between CreateProcess and assignment. An abrupt helper death during
that pre-assignment window can leave a suspended process; it has not run fixture
code but this window is not claimed as fully qualified crash cleanup.
Same-user handle tampering/injection and malicious administrator/kernel behavior
are not contained by these tests. Runtime code/protected-store assurance remains
at Phase 1's synthetic scope. No production scheduling or observer enrollment.

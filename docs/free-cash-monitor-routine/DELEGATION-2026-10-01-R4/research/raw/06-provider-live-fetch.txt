  - Base URL: https://hg.cash/api/v1   (dev: http://dev.hg.cash/api/v1)
  - Auth: "Bearer Token authentication ... Authorization: Bearer cash_your_token_here";
    token format "cash_<64-char-hex>"; "Generate your API token in the account settings page".
  - Read endpoints (documented):
      GET /accounts                     -> accounts with balance, pendingFees, netBalance,
                                           status, currency (+ id, name, number, alias,
                                           platform{id,name}, company{id,name}), count
      GET /account/{id}/balance         -> id, balance, currency, pendingFees, netBalance,
                                           status enum{Operativa|Bloqueada|Cerrada}
        quoted description: "Returns the balance, pending fees, net available balance,
        currency, and account status for the authenticated user's account by ID."
      Reference data: GET /api/v1/transaction-statuses, GET /api/v1/transaction-types
        ("no auth required")
  - Write endpoints (must never be used by the routine): POST /transactions (cash-out),
    POST /checkouts, POST /alias-lookup.
  - Field mapping to the routine's four figures:
      account_status        <- status          (Operativa|Bloqueada|Cerrada)  YES
      balance_cents         <- balance          (decimal; x100)               YES
      pending_cents         <- pendingFees      (decimal; x100)               YES
      earnings_total_cents  <- NOT PROVIDED by this API                       NO
  - Access gate: KYC/B2B onboarding ("< 48h Onboarding", iGaming operators);
    no credentials in the repo.
=> Verdict: a genuine documented read-only balance API EXISTS, but (i) it does not
   expose a lifetime-earnings field, (ii) it belongs to a LATAM iGaming payout rail,
   and nothing in the repo ties the monitored account to HG.Cash.

[5] Cashfree Payouts — documented read API, but the token is POST-minted
URLs fetched: https://www.cashfree.com/docs/api-reference/payouts/v1/get-balance
              https://www.cashfree.com/docs/api-reference/payouts/v1/get-balance-v12
              https://www.cashfree.com/docs/api-reference/payouts/v1/authorize
              (via search: .../payouts/v2/authorize, .../payouts/v1/getting-started-with-payouts-apis)
================================================================================
Quoted / observed:
  - Base URL: https://payout-api.cashfree.com  (sandbox: https://payout-gamma.cashfree.com)
  - Read endpoint: GET /payout/v1/getBalance  (and /payout/v1.2/getBalance, +optional
    paymentInstrumentId). Description verbatim: "Use this API to get the ledger balance
    and available balance of your account. Available balance is ledger balance minus the
    sum of all pending transfers ...". 200 example:
      {"status":"SUCCESS","subCode":"200","message":"Ledger balance for the account",
       "data":{"balance":"214735.50","availableBalance":"173980.50"}}
    Required headers: Authorization (Bearer auth token) and Content-Type.
  - TOKEN IS MINTED BY A WRITE VERB: POST /payout/v1/authorize
      description: "Use this API to authenticate with the Cashfree system and obtain the
      authorization bearer token. All other API calls must have this token ... The
      generated token is valid for 6 minutes."
      Required headers: X-Client-Id, X-Client-Secret (+ optional X-Cf-Signature).
  - Fields: balance + availableBalance only. No account status; no lifetime earnings.
  - Access gate: merchant signup + "Payouts API enabled" (documented 403 "APIs not enabled").
=> Verdict: documented read endpoint exists, BUT every read needs a fresh POST-minted
   token that expires in 6 minutes. Under operator rule R1 (no earning/write action
   automatically) a daily run would either mint a token by POST each day (a write-class
   call to the payment provider) or hold long-lived client secrets. Neither is read-only
   in the verb sense. Also: no lifetime-earnings field; scope is merchant payout balance,
   and nothing links it to the monitored account.

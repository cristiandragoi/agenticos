  Element order (RegistrationInfo, Principals, Settings, Triggers, Actions)
  deliberately mirrors a real task already registered on THIS host
  (\cua-driver-serve, exported with `schtasks /Query /TN "cua-driver-serve" /XML`),
  so the sequence matches what this Windows build itself produces.

  Chosen semantics and why:
    StartBoundary 2026-10-02T09:00:00  => the day AFTER the delegation date. A
                                         StartBoundary in the past, combined with
                                         StartWhenAvailable=true, fires ONE
                                         catch-up run at registration time; that
                                         catch-up would consume the day's R1 lock
                                         before the read source is populated
                                         (see SCHEDULER-SPEC.md precondition P1).
                                         Set the date to the day AFTER your
                                         intended first real run.
    StartWhenAvailable=true            => a missed 09:00 (machine asleep/off) is
                                         fired once when the machine is next
                                         available instead of being lost.
    MultipleInstancesPolicy=IgnoreNew  => a slow run can never be stacked by the
                                         next trigger.
    NO RestartOnFailure                => failure semantics are explicitly
                                         "no retry-until-success loop" (spec
                                         section 6). A failed read leaves the day
                                         lock in place; the watchdog reports it.
    RunLevel=LeastPrivilege            => the /RL LIMITED equivalent. NEVER
                                         HighestAvailable: nothing here needs
                                         elevation.
    LogonType=InteractiveToken         => per user, interactive session only. The
                                         toast transport needs a real desktop
                                         session; S4U or PASSWORD would run
                                         without one and the balloon would go
                                         nowhere.
    ExecutionTimeLimit=PT10M           => the whole run is a few seconds of file
                                         I/O; ten minutes is a generous ceiling.
